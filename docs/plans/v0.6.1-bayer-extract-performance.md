# V0.6.1 Bayer Extract 正确性与性能优化

## 问题 1：窗口只增大、不缩小

仅调用 `resize()` 时，Windows 样式和当前布局的旧 size hint 可能继续约束已经显示的非模态窗口。8×8 切回 2×2 后，矩阵滚动区虽然变小，但顶层窗口仍可能保留原尺寸。

修复为每次 block 尺寸变化后重新计算内容尺寸，并同步设置矩阵区固定高度和对话框固定尺寸。自动化测试验证 2×2 → 8×8 → 2×2 后窗口尺寸精确回到初始值。

## 问题 2：全选结果看起来不是原图

坐标枚举在完整 block 中是恒等映射，但此前存在两个后续问题：

1. 宽高不是 4×4/8×8 整数倍时，结果尺寸按完整 block 向上取整，产生原图不存在的黑色补位行/列。
2. 提取结果总会重新采样为最长边 2048 的 RGBA 预览，而 UInt16 原图使用完整分辨率 Grayscale16。即使像素映射相同，两者也走了不同显示数据和分辨率路径。

现在检测到所有矩阵位置均选中时，将操作定义为恒等操作：结果宽高严格等于原图；完整原图请求直接共享原始 `IPixelSource`、Grayscale16/RGBA 预览和 signal preview，不遍历像素、不分配新图，也不增加黑边。

## 已实施性能方案

- **全选零拷贝快速路径**：O(1) 组装结果，共享不可变原图资源。
- **单位置坐标预计算**：标准 Bayer、Quad、Hex 的常见单点提取预先计算 X/Y 源坐标，内层循环不再重复执行通用 block 映射。
- **有界预览从 2048 调整为 1024**：当前主视口约 840 px，预览读取量由最多约 315 万像素降至约 79 万像素，约为原路径的 1/4。
- **消除重复 RGBA 生成**：后台只生成原始 signal preview，统一由显示映射阶段生成一次 RGBA，不再在后台和 UI 各生成一次。

代价是非全选结果在高倍缩放时，底图预览分辨率上限为 1024；像素查询仍直接读取原始 RAW 坐标，因此数值不受影响。

## 后续可选方案

1. **按视口瓦片实时读取（推荐长期方案）**：缩放时按需生成原始分辨率瓦片，兼顾速度和高倍细节，但需要扩展 `ImageViewport` 的瓦片渲染接口。
2. **生成完整提取缓冲区**：初次耗时和内存占用较高，例如单个 11776×8842 UInt16 通道约 52 MB；重复浏览快，但不符合当前避免整图副本的约束。
3. **进一步并行化 1024 预览**：收益有限且会增加线程调度复杂度，当前不优先。

## 验证

- 2×2、4×4、8×8 全选在 5×3 非整倍数图像上均保持 5×3、末像素映射正确，并共享原始像素与预览指针。
- 4096×3072 单通道提取只生成 1024×768 signal preview，不生成重复 RGBA。
- 11776×8842 实际 UInt16 RAW 验证 8×8 全选零拷贝以及 2×2 左上角 5888×4421 坐标结果。

2026-08-18 Release 实测：同一 11776×8842 文件的 8×8 全选提取为 0 ms，2×2 单位置 1024 preview 提取为 15 ms；包含文件映射验证和全图统计的整项集成测试为 1263 ms。该时间是当前设备单次测量值，不作为跨设备硬性门限。
