# ADR-0001：桌面技术基线

- 状态：提议
- 日期：2026-07-30
- 决策者：待用户确认
- 关联需求：V0.1、UI-001～UI-005、DATA-001～DATA-006

## 背景

Raw Viewer 需要桌面三栏 UI、普通图片/RAW 读取、非破坏性处理、五步撤销、图像统计和超过 2 亿像素的大图浏览。项目还要求长期维护和清晰分层。

## 候选方案

### 方案 A：C++20 + Qt 6 Widgets + CMake

- 优点：桌面控件成熟；文件系统、设置、撤销、并发和 OpenGL 集成完整；C++ 易于控制内存、端序、SIMD 和瓦片。
- 缺点：构建环境和 C++ 工程复杂度较高；Qt 许可必须认真确认。
- 风险：若层次隔离不足，业务逻辑容易进入 QWidget；若直接使用 QImage 整图复制，大图仍会失败。

### 方案 B：Python + PySide6 + NumPy

- 优点：原型快，统计和脚本生态丰富。
- 缺点：发布体积、二进制依赖、GIL/跨线程边界和 400 MB 数据副本更难控制。
- 风险：原型代码可能成为长期生产核心，后期重写成本高。

### 方案 C：C# + .NET 桌面框架

- 优点：Windows 桌面开发效率高，工具链完善。
- 缺点：若未来跨平台，UI 选择和图像渲染路径需重新评估；高性能原生算法仍可能需要互操作层。
- 风险：原生/GPU/大文件缓冲跨边界管理增加复杂度。

## 决策

提议采用方案 A：

- C++20；
- Qt 6 Widgets；
- CMake + CMake Presets；
- Windows x64 作为首发平台；
- Qt 仅存在于表现层和基础设施适配器，领域层保持标准 C++；
- 渲染、解码、统计均通过应用端口隔离。

## 后果

### 正面影响

- 能用同一技术栈覆盖 UI、文件、线程和渲染；
- 大图路径可以逐步从 CPU 原型升级到 GPU 瓦片；
- 核心算法可脱离 UI 进行单元测试和基准测试。

### 负面影响与债务

- 需要建立一致的 CMake target 和依赖管理；
- 团队需要具备现代 C++、Qt 线程边界和 GPU 资源管理能力；
- 正式分发前必须完成 Qt 许可审查。

## 验证与复审

在第一阶段结束前验证：

- Windows x64 干净环境可重复构建；
- 可打开 8/16-bit 小型 RAW 和普通图片；
- UI 线程在读取/统计任务中保持响应；
- 领域库不链接 Qt Widgets。

如果无法满足大图峰值内存或团队维护成本不可接受，重新评估此 ADR。
